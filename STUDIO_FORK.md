## 0. Three facts that shape everything

1. **Upstream moves fast.** 960 commits in the last 30 days: 376 touch `apps/app`, 286 `apps/server`, 317 `plugins/`, 126 `packages/plugin-sdk`. The hottest files are exactly the ones a deep integration wants to edit: `ThreadDetailView.tsx` (35 commits), `SettingsView.tsx` (34), `RootComposeView.tsx` (19), `plugin-sdk-app-impl.tsx` (19), `plugin-slots.ts` (15), `ThreadSecondaryPanel.tsx` (15), `AppLayout.tsx` (14).
2. **Three of the "plainly in use" plugins are not in use on the live BB (now decided: remove).** `github` is disabled (row untouched since 15 Oct), `bb--mcp` is disabled, and `memory` was never installed. What is live instead: `bb--git` and `bb--github-pr-status` (running), and MCP through Patrick's own `agent-plugins` plugin (511 `agent_plugins_call` tool calls in 30 days). See question 1.
3. **A removed builtin loses its data on first boot.** `removeUnbundledBuiltins()` (`apps/server/src/services/plugins/plugin-service.ts:1387`) deletes the row, settings, secrets and schedules of any builtin no longer in the registry (KV stays). Migrations are forward only, and the fork is at 0.49 while the live app is 0.48.2. So the fork must run on a copy of `~/.bb`, never the live one, until the plugin set is settled.

## 3. Proposed shape

**Recommendation: a thin patch stack rebased on `upstream/main`, with Studio staying a plugin that the fork bundles as a builtin.** Not a hard fork, and not Studio code moved into `apps/app`.

Why:

- At 960 upstream commits a month, every line edited in a hot core file is a recurring conflict. A hard fork goes stale within weeks.
- Moving Studio's 89,000 lines into core buys nothing the plugin boundary blocks. What Studio lacks is about a dozen extension points, not access to core's internals.
- Bundling Studio as a builtin already removes the install flow, the Setup page and (if question 2 allows) the SDK pin.

### The stack, in order

1. **`fork: identity`.** App id, name, data dir, updater off. About 5 files.
2. **`fork: strip plugins`**, as two commits:
   - _Unregister_: the baseline files listed in section 1 plus the tests that enforce the set. Hand-written and small.
   - _Delete directories_: produced by a script (`scripts/fork/strip-plugins.mjs`, reading a list of names) and always the last commit on the branch. On each sync, drop it, rebase, and run the script again. Deleting by hand would hit a modify/delete conflict every time upstream touches `plugins/tasks` (15 commits a month) or `plugins/docs` (17).
3. **`fork: bundle studio`.** Add Studio to `BUILTIN_PLUGINS`. Bring the source in as a git submodule at `plugins/studio` pointing at `bb-studio`, so Studio's history and agents stay in their own repo.
4. **`seam: <name>`**, one commit per seam. Rules that keep each one cheap to rebase:
   - New behavior lives in new files. Suggested home: `apps/app/src/studio-native/` and new SDK members.
   - An edit to an existing upstream file is a few lines that call into the new file. No reformatting, no moved code.
   - Each seam is a generic extension point with an `experimental_` name and a `docs/api_to_audit.md` entry, as the repo's rules require. That also makes each one a candidate to send upstream, which is the only way a patch stops costing rebase work. Sending is Patrick's call; I will not push or open anything.
   - No runtime feature flags. The fork is the flag. A flag on every seam doubles the paths to test and upstream would not carry them anyway.

### Sync routine

Weekly: `git fetch upstream`, drop the delete commit, `git rebase upstream/main` with `rerere` on, rerun the strip script, then `pnpm exec turbo run typecheck build`. Track the patch list in this file. If a seam conflicts twice in a row, it is edited too deeply and should be reshaped.

### Build first

1. **Runnable fork (stack items 1 to 3).** Proves the loop: strip, bundle Studio, build, run on a copy of `~/.bb`, rebase once. No product change yet.
2. **Seam 3, routing.** Small, mostly additive, deletes Studio's most fragile code, and seams 1 and 2 need it.
3. **Seam 2 in its slot form, then seam 1.** Shared new tab first, because it is cheap and visible. Then the shared pane and tab model, which is the real prize and the most expensive patch.

After that, by payoff per conflict risk: 6 (search), 8 (notifications), 4 (sidebar), 5 (thread view), 10 (orchestration).

### Risks

- **Seam 1 lands in files upstream is actively changing.** If upstream reworks split panes, the patch is rewritten, not rebased. Mitigation: keep the pane-kind addition as a registry that core's own kinds also use.
- **Data.** See fact 3. Phase 2 verification should use a copied data dir, and the fork needs its own data dir from the first commit.
- **Two Studios.** If Studio must keep installing on stock BB, every seam needs a fallback path in Studio, and the old hacks stay in the codebase. That halves the payoff of section 2.

## 4. Phase 2 plan (after sign-off)

1. Unregister and delete the 15 "Remove" plugins, plus whichever "Unsure" ones are approved. One commit for the unregister, one scripted commit for the deletes.
2. Fix the tests and Turbo entries the audit named.
3. Verify: `pnpm exec turbo run typecheck`, then `pnpm build`, then the server plugin tests (`--filter=@bb/server`), with output piped to a file.
4. No identity, bundling or seam work until the shape in section 3 is agreed.

## Open questions

1. **github, memory, mcp.** Answered 10 Nov: remove all three. They are now in the Remove table.
2. **Must Studio keep installing on stock BB** (the marketplace `stable` branch, other users)? If yes, seams need fallbacks and the SDK pin stays. If no, Studio can build against the fork's SDK and delete its workarounds outright.
3. **Is the fork meant to become Patrick's daily driver, or stay a testbed for changes to send upstream?** Daily driver means doing identity, updater and data migration first. Testbed means skipping those and going straight to seams.

### Corrections to section 2

- **Seam 2 (shared new tab) needs no core change.** The New thread screen already renders plugin sections under the composer through the stable `homepageSection` slot (`apps/app/src/components/plugin/PluginHomepageSections.tsx`). No plugin uses it, Studio included. Studio can put its collection and recents there on stock BB today. The work is in `bb-studio`.
- **Seam 1 (shared panes) was half there already.** Core's split layout accepts a plugin page as a pane, and a modifier-click on an in-app link opens one. What plugins lacked was a way to open, list, focus and close panes from code; `e03f0dd6a5` adds that. Still missing for Studio to retire its workspace: several tabs inside one pane. That is a layout change in `SplitThreadArea.tsx` (1,700 lines, edited upstream most weeks), not an API.

### Retention findings

- **Existing export.** `bb thread log --format json --all` prints a thread's stored events. There is no file export, no JSONL, and nothing tied to deletion. `packages/server-archive` archives a whole data dir for server moves.
- **Deleting does shrink `bb.db`, slowly, with no manual VACUUM.** Delete marks the thread, a background purge removes its event rows in batches (`packages/db/src/data/thread-purges.ts`), and an hourly check runs an incremental vacuum of at most 20,000 pages, about 78 MB, when at least 1,024 pages are free (`apps/server/src/services/system/periodic-sweeps.ts`). The live database is in incremental mode with no free pages: 786,367 pages of 4 KB. 1,390 of its 1,761 threads are archived.
- **What the export holds.** The event table as it is at delete time. Event pruning has already dropped superseded streaming deltas and usage snapshots; completed messages, tool calls and results remain. Attachments and thread storage files are not exported.

### Test fallout from the strip (decided)

A full `turbo run test` after the strip failed 13 tests in `@bb/server`, `@bb/web`, `@bb/plugin-build` and `@bb/scripts` that use Docs, GitHub, Memory, Tasks or the Modal sandbox as live fixtures. Typecheck and build do not see this.

Decision (10 Nov): all 15 plugins stay removed. The strip script skips those tests from `scripts/fork/skipped-tests.json` (`b0385ceba3`, generated result `2296369e64`), so there are no hand edits to conflict. After it, the server, web and plugin-build suites pass.

## Version line, updates and releases (12 Nov)

**Version line.** BB Studio has its own semver, independent of bb's, in `apps/desktop/studio-release.fork.json`. It started at 1.0.0: copies installed before it report bb's 0.49.x, and electron-updater only offers a higher version, so anything below 1.0.0 would never reach them. `apps/desktop/package.json` keeps bb's version (it is the "based on" version); the build replaces it. `scripts/build.mjs` ends its esbuild defines with `studioBuildDefines(readStudioBuild(process.env))` (`scripts/studio-release.fork.mjs`), so `BB_DESKTOP_VERSION` is the Studio version and `BB_STUDIO_BUILD` carries the version, the bb base from `studio-upstream.json` and the feed. `scripts/run-electron-builder.mjs` calls `applyStudioBuilderConfig`, which sets `extraMetadata.version` (the packaged `package.json`, `CFBundleShortVersionString` and `app.getVersion()`, the version electron-updater compares) and `publish`. About shows `Version: 1.0.0 (based on bb 0.49.0 @ 030b1b7)` (`studioAboutVersion` in `main.ts`); Settings, Updates shows the Studio version with "based on bb 0.49.0 @ 030b1b7" beside it: `ForkStudioBase.tsx` in `RowName` draws it next to any row whose version is the build's (`window.bbDesktop.experimental_studioBuild`). With the server run by the desktop, that row is "Server" and comes from the server's view of the desktop updater; `desktop-app-update.ts` reports the desktop's version there, since the bundled server's own version is bb's.

**Updates.** The feed is the GitHub releases of `patleeman/bb-studio` (`provider: github`, no token), the public repository that is to hold the clean monorepo; it is `updates` in `studio-release.fork.json`. The app-update.yml in the bundle and the runtime `setFeedURL` both use it; upstream's version check reads `desktop-version.json` from `https://github.com/patleeman/bb-studio/releases/latest/download/`. `DESKTOP_UPDATES_ENABLED` is `STUDIO_UPDATES_ENABLED`: on in every build made by `scripts/build.mjs`. electron-updater offers only the latest published, non-draft, non-prerelease release, so drafts are never offered, and every published release must carry `latest-mac.yml`. While the repository has no published release with `latest-mac.yml` (on 12 Nov it is public with no releases; a private repository answers 404), every check fails: upstream's services log it to `desktop.log` and keep the state as it was, with no dialog and no toast. Settings, Updates shows "No BB Studio release found." with Check on the Server row (the message is `STUDIO_NO_RELEASE_MESSAGE` in `desktop-app-update.fork.ts`; the button's labels come from `forkStudioCheckLabel` in `ForkStudioBase.tsx`); nothing else (no sidebar badge). In a Studio build the row's Changelog is a link to `https://github.com/patleeman/bb-studio/releases` once the check found a release, and is hidden while it found none (`forkStudioReleaseLink`); bb's own changelog panel is never offered. The feed starts working, with no change to the app, when a release with the update files is published there. electron-builder writes `app-update.yml` only for a zip or DMG target: an install from `pnpm run package` (`--dir`) can see an update but not download it (logged, no dialog), so update-capable installs come from the release script's DMG.

**Release.** In the desktop worktree, with `CSC_NAME` set to the Developer ID identity and the `bbstudio-notary` notarytool profile in the keychain:

It folds the new version into the commit that owns `studio-release.fork.json`, regenerates into `desktop-candidate` with `sync.mjs --checks none`, checks that only the version changed, and prints the promote, import and push commands. Run them.
2. `node scripts/fork/release-desktop.mjs --no-bump --notes-only` drafts the notes from the commits since the last Studio tag (`--since <ref>` to choose) into `../.bb-studio-fork-sync/release-notes-v<version>.md`. Edit it. The first line names the Studio version and the bb base.

## Import and one-way mirror of bb (10 Nov)

BB Studio starts as a copy of the bb install on the same Mac and then follows it one way. All of it is in `apps/server/src/services/fork-import/` (seam `import-sync`). Core has small hooks in seven files: `server.ts` registers the routes (which also start the jobs), `start-server.ts` calls `forkBeforeDatabase`, `thread-send.ts` calls the fork's write guards, `thread-create.ts` asks the fork's host stand-ins before refusing a fork onto another machine, `dispatch-attempt.ts` lets an empty-input fork start without a turn while a limit is full, `apps/cli/src/commands/server.ts` registers the `bb server mirror` commands, and the CLI command index lists them.

**First run** (`first-run.ts`). When the data dir has no `bb.db`, the server imports before it opens the database. The source is `~/.bb` for the packaged app (data dir `~/.bb-studio`), or the path in `BB_STUDIO_IMPORT_FROM`; `BB_STUDIO_IMPORT_FROM=off` turns it off. A dev data dir imports only when the variable names a source. It takes snapshots of `bb.db` and every plugin database with SQLite's backup API (the source is opened read-only and never written), copies the other server-owned files, and installs them with bb's own import code, so the path fixups and the connect hold of a manual import apply. Thread storage is copied after the server is up (the sweep job `fork-import-thread-storage`, once), so a large install does not hold up the start; the packaged app waits up to ten minutes for the first start (`STARTUP_TIMEOUT_MS`, set by `identity.mjs`).

**What is left out or turned off.** The source's host identity (`host-id`, `auth.json`), `telemetry-id`, the Mobile and push-notifications plugin folders (APNs key, relay token), push device tokens, the Account Pooler's logins and hub tokens (`plugins/account-pool/secrets`), its quota, pins and active accounts (`account_quota`, `pool_affinity`, `pool_active_account`) and its refresh-rejection and thread routing records (`rejected-refresh:`, `routed:`, `retry-route:` keys), daemon sessions, queued messages, pending approvals and terminals. Threads that were running at the source are stored as idle. The source's rail and sidebar-footer preferences (`sidebar.pluginPanelOrder`, `sidebar.visiblePluginPanels`, `sidebar.hiddenFooterItems`, `sidebar.footerOrder`) are dropped so upstream's rail and footer defaults apply; every other preference is kept. The plugins `mobile`, `push-notifications`, `automations` and `storage-retention` are imported disabled; automations rows are disabled. Turning push or automations on again is a deliberate step in Settings. The Account Pooler keeps bb's account list (ids, labels, order) and routing switches, so each account shows signed out until it is signed in here. A refresh token is single-use: a copied login dies on the first refresh by either app, and copied quota hid that (BB Studio showed bb's numbers and answered 429 with bb's reset date).

**Optional import file.** `<data dir>-import.json` beside the data dir (for the packaged app: `~/.bb-studio-import.json`) can hold `pluginPaths` (`{ "studio": "/path/to/plugin" }`: load a path-installed plugin from another folder) and `keepPlugins` (a list: every other added plugin, meaning not built in, is imported disabled). `uiPreferences` (`{ "sidebar.threadListProvider": "studio/everything" }`) sets UI preferences in the imported copy, so the source's choice of thread list does not come along. Without the file, added plugins keep their folders and stay as they were.

**Sync** (`sync.ts`, every minute as the job `fork-import-sync`). The fork's three jobs (`fork-import-sync`, `fork-import-thread-storage`, `fork-import-plugin-sync`) run on their own 10-second timer (`sweeps.ts`), started by `registerForkImportRoutes` only after `forkBeforeDatabase` named the data dir. They keep bb's sweep rules: per-job cadence, background jobs not awaited, no overlap, nothing while a server move has frozen the database, not started on a pending move target, and stopped on SIGINT/SIGTERM. Upstream's `periodic-sweeps.ts` is not edited. Projects, thread sections and environments are upserted by `updated_at`. A thread is copied again when its row changed or it has new events (found by event rowid above the last one seen). New events are appended; when the count of earlier events differs (bb prunes and deletes events), that thread's events are reloaded. The thread's per-thread tables are reloaded with it. Threads deleted at the source are removed here (checked every 10 minutes). Environments keep the source machine as their host, so BB Studio never runs cleanup on a folder bb still uses. `fork-import.db` in the data dir holds the cursors and the list of mirrored threads.

**Plugin data** (`plugin-sync.ts`, every 5 minutes). For each plugin database present on both sides, every table both sides have is compared row by row against the source as it was at the last sync. `fork-import.db` keeps that baseline: one content hash per row (`plugin_rows`, keyed by the table's primary key), so no table depends on `updated_at` or on a cursor. A row whose hash changed at the source, or a new source row, is written here with a plain `UPDATE` or `INSERT` (never an upsert, whose conflict policy would override `INSERT OR REPLACE` in Studio's `items` triggers), unless the table has `updated_at` and the row here is newer. A row deleted at the source is deleted here unless it was edited here since the last sync. A row that exists only here is never touched, and a row that fails is noted and retried next time without holding up the rest of the table. A table without a primary key is compared as a whole: changed only at the source, it is reloaded; changed on both sides, it is kept and noted. A table seen for the first time, or whose shared columns changed, takes its baseline from the rows here, so a copy that missed updates catches up without losing its own rows. Studio's Todos (`bot_loops`, `loop_events`) are mirrored; Studio's Bot, runner, automation, Todos scheduler (`loop_scheduler`), suggestion and account warning (`account_warnings`) tables are never synced, nor is the Account Pooler's database, nor are tables only this side has (`bot_threads`, `memory_records`, `triggers`, `items` and the like). At import the Bot is stopped, runners and Studio automations are paused, cache keep-warm is off and Todos' scheduler (`loopsEnabled`) is off. A plugin whose database layout is newer at the source is skipped until this side catches up.

**Mirrored threads are read-only** until taken over: `ensureThreadIsWritable` calls the fork's write guards (`services/threads/thread-write-guards.fork.ts`, one line in `thread-send.ts`), and the import registers one that refuses a mirrored thread with a 409 `thread_read_only`, details `{ reason: "mirrored" }` and the mirror message. It is not a `thread_not_writable` reason: the app draws those with fixed copy per reason, and none fits; for any other error code the app shows the server's message, so the contract enum and `lifecycle-errors.ts` stay upstream's. **Take over** (`takeover.ts`) is refused while the thread is running or has queued messages at the source. It runs one last sync, moves the thread's environment to this machine, and stops syncing that thread and that environment. From then on the two copies are separate.

**A thread from a mirrored message.** A fork must run on its source thread's machine, and a mirrored thread's environment stays on bb's machine, which never connects to BB Studio. `assertForkSourceHost` (`thread-create.ts`) asks the fork's host stand-ins first (`services/threads/thread-fork-hosts.fork.ts`); the import registers one that lets a mirrored, not taken over thread whose environment is on the imported bb machine fork onto this machine. The new thread is BB Studio's own: it copies the history up to the message, starts no turn and writes nothing to bb. The mirrored thread stays read-only and its environment stays on bb's machine. Reply in thread forks with an empty input, which upstream starts as an idle fork with no turn. Upstream still sent that first dispatch through the plugin hooks and core waits, so a full concurrency limit queued an empty message that every later read rejected with "Stored queued message … is malformed". `startsNoTurn` (`services/threads/turnless-dispatch.fork.ts`) marks the first dispatch of a pending fork with no input: `dispatch-attempt.ts` skips the plugin hook pass for it, so the limit does not hold it, and a core wait (an update hold, an offline host) leaves the fork pending instead of queueing an empty message. A fork with input is held and queued as before. Studio's Reply in thread and Fork conversation from here pick the environment here (a ready environment for the same folder, else a personal workspace in the personal project, else the folder, else the project default).

**Commands.** `bb server mirror status | sync | pause | resume | thread <id> | take-over <id>`; the routes are under `/api/v1/fork/import`.

**Not covered.** An event edited in place at the source without a new event is not noticed until that thread's event count changes. Projects, thread sections and environments deleted at the source stay here.

## Syncing with upstream (10 Nov)

**Stack order.** The branch is four layers on top of the upstream base:

1. `fork: rules, tooling and notes`: the scripts in `scripts/fork/`, this file, `docs/api_to_audit.fork.md`, and one line each in `AGENTS.md`, `CLAUDE.md` and `vitest.shared.ts`.
2. Seams. `seam: SDK tables` holds every fork edit to the SDK's shared files, the backend contract and the Plugin Guide. `seam: core hooks` holds every upstream app, server and desktop file that more than one seam edits (`AppLayout.tsx`, `plugin-api.ts`, `plugin-service.ts`, `lifecycle-outcome.ts`, `apps/server/src/server.ts`, the desktop `main.ts` and `preload.ts`, `desktop-contract/src/info.ts`, `plugin-navigation-hooks.ts`, `ThreadScreen.tsx`, `SecondaryPanelTabStrip.tsx`, `ThreadTimelineRows.tsx`). The other `seam:` commits hold the implementations and the core files only they edit.
3. Features: one commit per area (search, workbench, sidebar, quiet turns, layout and composer, import, diff, polish).
4. Generated commits at the tip, each with a `Fork-Generated:` trailer: strip, identity, rebrand. Never rebase these. Drop them and run the scripts again.

Each upstream file the fork edits is in exactly one hand commit, so a conflict in it stops one pick. Add new work as a new commit in layer 2 or 3 (below the generated commits), or fold it into the commit for its area; an edit to a file that `seam: SDK tables` or `seam: core hooks` already holds goes into that commit.

**Rules that keep conflicts small.**

- Run `oxfmt` only on fork-owned files, never on an upstream file the fork touches.
- A new slot goes in `packages/plugin-sdk/src/internal/fork-slots.ts` and `apps/app/src/lib/fork-slots.ts`, not in the upstream tables.
- A test the fork breaks on purpose goes in `scripts/fork/skipped-tests.json`. `scripts/fork/vitest-skips.ts` skips it at run time; test sources stay as upstream wrote them.
- Edits that only exist because plugins were removed (registry, marketplace list, stories, Plugin Guide examples) live in `scripts/fork/patches/unregister.patch`. To change it: reverse it (`git apply -R`), edit the files, and write the diff of those files back to the patch.
- API audit entries go in `docs/api_to_audit.fork.md`.

**Regenerating by hand.** Order matters: `node scripts/fork/strip-plugins.mjs` (it runs `pnpm install`), then `node scripts/fork/identity.mjs`, then `node scripts/fork/rebrand.mjs`. The rebrand needs the install first because the app's icon generator imports `sharp`.

**Who syncs.** An agent does, daily, from a bb automation; `scripts/fork/sync-agent.md` is its brief. It resolves conflicts itself and reports only when it could not, or when checks fail. Sync cost is measured in conflicts and how hard each one is. The rules that keep them easy are in `AGENTS.fork.md`; `scripts/fork/core-edits.json` records the intent of every core edit, and `scripts/fork/check-core-diff.mjs` enforces the list and the line budgets.

**`scripts/fork/sync.mjs`.** `node scripts/fork/sync.mjs --fetch` replays the fork onto `upstream/main` in a throwaway worktree under `../.bb-studio-fork-sync/`: it cherry-picks the hand commits (git rerere replays recorded conflict resolutions), checks the core diff against the ledger, runs the three scripts, commits their output with the trailer, and runs typecheck, build and the server, web, plugin-build and SDK tests (`--checks none|quick|full`). It writes a report beside the worktree. On success it moves the local branch `exp/studio-native-candidate` and nothing else; it never checks out or moves `exp/studio-native`, and it pushes nothing. On a conflict it stops, leaves the worktree, and prints the commands to continue. With `--onto` set to the current base it is a reproduction check: the result must have the same tree as the source branch.

## Monorepo (12 Nov)

The fork lives in the BB Studio monorepo, on its `desktop` branch. It replaces the local-only branch `exp/studio-native` of the old `bb` clone; where older sections of this file say `exp/studio-native`, `exp/studio-native-candidate` or `bb-studio-native`, read `desktop`, `desktop-candidate` and `bb-studio-app-desktop`.

- **`desktop` branch** (worktree `~/workingdir/bb-studio-app-desktop`): this stack, unchanged in shape. Paths are bb-root-relative, it descends from `upstream/main`, and each sync rewrites it. The ledger, `check-core-diff.mjs` and the reproduction check run here.
- **`main` branch** (worktree `~/workingdir/bb-studio-app`): the monorepo. `desktop/` there is a tree snapshot of this branch, written by `scripts/import-desktop.mjs` as a merge commit whose second parent is the stack tip. Nobody edits `desktop/` on `main`. `plugins/` there is the Studio plugins with their history, in their own pnpm workspace.
- **Invariant:** `git rev-parse main:desktop` equals `git rev-parse 'desktop^{tree}'` (`node scripts/import-desktop.mjs --check` on `main`).
- **Scripts.** `sync.mjs` defaults to `--source desktop --candidate desktop-candidate`, refuses to run inside `main`'s `desktop/`, and takes its work folder from `BB_STUDIO_SYNC_DIR` (default `../.bb-studio-fork-sync`, as before). `check-core-diff.mjs` has the same refusal. `build-plugins.mjs`, with no arguments and no `~/.bb-studio-import.json`, builds every package in `../bb-studio-app/plugins/packages`.
- **Remotes.** `origin` is the BB Studio repository (the `pre-push` hook on `main` names it). `upstream` is `get-bb/bb` with the push URL set to `DISABLED`, only `main` fetched and no tags. A `pre-push` hook on `main` (`scripts/git-hooks/pre-push`) refuses every other remote and every ref but `main`, `desktop` and `v*` tags. GitHub Actions is off for the repository, so upstream's workflows at this branch's root do not run.

Daily flow:

1. `node scripts/fork/sync.mjs --fetch` here. It moves only `desktop-candidate`.
2. Promote: `git reset --hard desktop-candidate` on `desktop`, with a clean tree.
3. `node scripts/import-desktop.mjs` on `main`.
4. `git push origin main && git push --force-with-lease origin desktop`.

A core change outside a sync: commit it below the generated commits, run `check-core-diff.mjs`, regenerate with `node scripts/fork/sync.mjs --source <work branch> --onto <current base> --candidate desktop-candidate`, promote, import. `docs/REIMPORT.md` on `main` has the commands.

## Roadmap (approved 10 Nov)

Worked in this order, one milestone at a time. Core edits are allowed but stay small and ledgered; local branches only; each chunk is checked on the second instance before `:24300` restarts. iPhone work is on hold, and changes should stay easy to lift into a separate repo.

0. Quiet turns (`[PASS]`) and the rail cleanup.
1. Delete dead folders and files in bb-studio on the local exp branch: bb-canvas, bb-studio-canvas, bb-studio-code, bb-studio-decisions, bb-studio-kit and bb-studio-applets leftovers (only `dist/` and `node_modules`), plus other stale files. List them in the report first.
2. One scheduler: Studio runners, Bot automations, loops triggers and BB automations as one scheduling model and one UI (one list, one create flow, one run history). Runners already sit on BB automations.
3. Output surfaces become two kinds. Pages: documents; designs and slide decks become page types or views. Apps: minis; dashboards and artifacts that are HTML or interactive become apps. Old ids keep resolving, data is migrated, agent tools keep working through aliases.
4. Missing core features: plugin approval dialogs (replacing the nonce workaround); plugins handle link clicks in chat replies; rename an open workbench tab; Bot events for interrupts and daemon restarts (removing the 60 s and 5 min polling); Global workbench tabs synced server-side instead of localStorage.
5. VS Code: a real workbench tab kind, one per project or worktree, Global-able; agent edits from Claude Code and Codex stream into the open editor through a core file-change event; BB diff to VS Code at the hunk; "New thread from selection" and "Ask about this" in VS Code; live theme from the SDK hook; Cmd+K chords handed back to VS Code when it has focus; one "Open in" model. Includes the file-opener fix from get-bb/bb #5614.
6. Window API and HUD: a plugin SDK API to open and style Electron windows (size, transparent, alwaysOnTop, clickThrough, global hotkey, menu bar icon); the HUD as the first app (a transparent floating Bot transcript with input, mockup 1d); pop any item out into its own window. Needs the desktop app run from source in a dev Electron build on the data copy, never the packaged app. Visual Chat then becomes a separate app inside BB Studio: its own window, its own launcher entry and hotkey, not a sidebar item or workbench tab. It stays its own package (the `studio-visual-chat` id is unchanged, so the iPhone tab keeps working) and sessions still link to their thread. Order: window API, HUD, Visual Chat as the second app, then pop-out for items.

Deferred to the identity step: app ids and data dirs, the desktop rebrand, and folding Mobile and Visual Chat into the Studio plugin (one iOS build covers both).

### Changes from the published palettes

- One Dark: the palette is published in HSL; the hex values are converted.
- Solarized Light: the body text is base01 (`#586e75`), not base00, and the sidebar is base3, not base2. base00 on base3, and base01 on base2, are below 4.5:1.
- All themes: muted text, error, warning and success text are mixed toward the theme's text color at run time until they reach 4.5:1 (3:1 for success and accent) on every surface (`src/theme/look.ts`). The fills keep the published colors.

### Methods

- Event Horizon traces light through a Schwarzschild black hole. Each ray from the camera is stepped with the photon orbit equation in Cartesian form, `a = -3/2 · h² · x / r⁵` (Schwarzschild radius 1, `h = |x × v|`), which gives the same path as the Binet equation `u'' + u = 3Mu²`. The step is 0.12·r, so a pixel takes more steps near the hole and none when its ray misses the 18 r_s sphere; outside that sphere the weak-field angle `2 r_s / b` bends the ray. The disk runs from the innermost stable orbit (3 r_s) to 16 r_s with the Novikov–Thorne flux profile `F ∝ r⁻³(1 − √(r_in/r))`, temperature `T ∝ F^¼`, Keplerian speed `β = √(M/(r − 2M))`, and the shift `g = √(1 − r_s/r) / (γ(1 − β·n))`. Observed temperature is `g·T` and brightness `g⁴·F`, so the approaching side is brighter and bluer.
- Forest's sun is placed with the low-precision solar coordinates of the Astronomical Almanac (accurate to about 0.01° between 1950 and 2050): day above 6°, night below −6°, dawn or dusk in between. With no place, the clock stands in: sunrise at 6:30, sunset at 18:30.
