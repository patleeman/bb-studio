## 0. Three facts that shape everything

1. **Upstream moves fast.** 960 commits in the last 30 days: 376 touch `apps/app`, 286 `apps/server`, 317 `plugins/`, 126 `packages/plugin-sdk`. The hottest files are exactly the ones a deep integration wants to edit: `ThreadDetailView.tsx` (35 commits), `SettingsView.tsx` (34), `RootComposeView.tsx` (19), `plugin-sdk-app-impl.tsx` (19), `plugin-slots.ts` (15), `ThreadSecondaryPanel.tsx` (15), `AppLayout.tsx` (14).
2. **Three of the "plainly in use" plugins are not in use on the live BB (now decided: remove).** `github` is disabled (row untouched since 15 Oct), `bb--mcp` is disabled, and `memory` was never installed. What is live instead: `bb--git` and `bb--github-pr-status` (running), and MCP through Patrick's own `agent-plugins` plugin (511 `agent_plugins_call` tool calls in 30 days). See question 1.
3. **A removed builtin loses its data on first boot.** `removeUnbundledBuiltins()` (`apps/server/src/services/plugins/plugin-service.ts:1387`) deletes the row, settings, secrets and schedules of any builtin no longer in the registry (KV stays). Migrations are forward only, and the fork is at 0.49 while the live app is 0.48.2. So the fork must run on a copy of `~/.bb`, never the live one, until the plugin set is settled.

## 3. Proposed shape

**Recommendation: a thin patch stack rebased on `upstream/main`, with Studio staying a plugin that the fork bundles as a builtin.** Not a hard fork, and not Studio code moved into `apps/app`.

Why:

- At 960 upstream commits a month, every line edited in a hot core file is a recurring conflict. A hard fork goes stale within weeks.
- Moving Studio's 89,000 lines into core buys nothing the plugin boundary blocks. What Studio lacks is about a dozen extension points, not access to core's internals.
- Bundling Studio as a builtin already removes the install flow, the Setup page and (if question 2 allows) the SDK pin.

### The stack, in order

1. **`fork: identity`.** App id, name, data dir, updater off. About 5 files.
2. **`fork: strip plugins`**, as two commits:
   - _Unregister_: the baseline files listed in section 1 plus the tests that enforce the set. Hand-written and small.
   - _Delete directories_: produced by a script (`scripts/fork/strip-plugins.mjs`, reading a list of names) and always the last commit on the branch. On each sync, drop it, rebase, and run the script again. Deleting by hand would hit a modify/delete conflict every time upstream touches `plugins/tasks` (15 commits a month) or `plugins/docs` (17).
3. **`fork: bundle studio`.** Add Studio to `BUILTIN_PLUGINS`. Bring the source in as a git submodule at `plugins/studio` pointing at `bb-studio`, so Studio's history and agents stay in their own repo.
4. **`seam: <name>`**, one commit per seam. Rules that keep each one cheap to rebase:
   - New behavior lives in new files. Suggested home: `apps/app/src/studio-native/` and new SDK members.
   - An edit to an existing upstream file is a few lines that call into the new file. No reformatting, no moved code.
   - Each seam is a generic extension point with an `experimental_` name and a `docs/api_to_audit.md` entry, as the repo's rules require. That also makes each one a candidate to send upstream, which is the only way a patch stops costing rebase work. Sending is Patrick's call; I will not push or open anything.
   - No runtime feature flags. The fork is the flag. A flag on every seam doubles the paths to test and upstream would not carry them anyway.

### Sync routine

Weekly: `git fetch upstream`, drop the delete commit, `git rebase upstream/main` with `rerere` on, rerun the strip script, then `pnpm exec turbo run typecheck build`. Track the patch list in this file. If a seam conflicts twice in a row, it is edited too deeply and should be reshaped.

### Build first

1. **Runnable fork (stack items 1 to 3).** Proves the loop: strip, bundle Studio, build, run on a copy of `~/.bb`, rebase once. No product change yet.
2. **Seam 3, routing.** Small, mostly additive, deletes Studio's most fragile code, and seams 1 and 2 need it.
3. **Seam 2 in its slot form, then seam 1.** Shared new tab first, because it is cheap and visible. Then the shared pane and tab model, which is the real prize and the most expensive patch.

After that, by payoff per conflict risk: 6 (search), 8 (notifications), 4 (sidebar), 5 (thread view), 10 (orchestration).

### Risks

- **Seam 1 lands in files upstream is actively changing.** If upstream reworks split panes, the patch is rewritten, not rebased. Mitigation: keep the pane-kind addition as a registry that core's own kinds also use.
- **Data.** See fact 3. Phase 2 verification should use a copied data dir, and the fork needs its own data dir from the first commit.
- **Two Studios.** If Studio must keep installing on stock BB, every seam needs a fallback path in Studio, and the old hacks stay in the codebase. That halves the payoff of section 2.

## 4. Phase 2 plan (after sign-off)

1. Unregister and delete the 15 "Remove" plugins, plus whichever "Unsure" ones are approved. One commit for the unregister, one scripted commit for the deletes.
2. Fix the tests and Turbo entries the audit named.
3. Verify: `pnpm exec turbo run typecheck`, then `pnpm build`, then the server plugin tests (`--filter=@bb/server`), with output piped to a file.
4. No identity, bundling or seam work until the shape in section 3 is agreed.

## Open questions

1. **github, memory, mcp.** Answered 10 Nov: remove all three. They are now in the Remove table.
2. **Must Studio keep installing on stock BB** (the marketplace `stable` branch, other users)? If yes, seams need fallbacks and the SDK pin stays. If no, Studio can build against the fork's SDK and delete its workarounds outright.
3. **Is the fork meant to become Patrick's daily driver, or stay a testbed for changes to send upstream?** Daily driver means doing identity, updater and data migration first. Testbed means skipping those and going straight to seams.

### Corrections to section 2

- **Seam 2 (shared new tab) needs no core change.** The New thread screen already renders plugin sections under the composer through the stable `homepageSection` slot (`apps/app/src/components/plugin/PluginHomepageSections.tsx`). No plugin uses it, Studio included. Studio can put its collection and recents there on stock BB today. The work is in `bb-studio`.
- **Seam 1 (shared panes) was half there already.** Core's split layout accepts a plugin page as a pane, and a modifier-click on an in-app link opens one. What plugins lacked was a way to open, list, focus and close panes from code; `e03f0dd6a5` adds that. Still missing for Studio to retire its workspace: several tabs inside one pane. That is a layout change in `SplitThreadArea.tsx` (1,700 lines, edited upstream most weeks), not an API.

### Retention findings

- **Existing export.** `bb thread log --format json --all` prints a thread's stored events. There is no file export, no JSONL, and nothing tied to deletion. `packages/server-archive` archives a whole data dir for server moves.
- **Deleting does shrink `bb.db`, slowly, with no manual VACUUM.** Delete marks the thread, a background purge removes its event rows in batches (`packages/db/src/data/thread-purges.ts`), and an hourly check runs an incremental vacuum of at most 20,000 pages, about 78 MB, when at least 1,024 pages are free (`apps/server/src/services/system/periodic-sweeps.ts`). The live database is in incremental mode with no free pages: 786,367 pages of 4 KB. 1,390 of its 1,761 threads are archived.
- **What the export holds.** The event table as it is at delete time. Event pruning has already dropped superseded streaming deltas and usage snapshots; completed messages, tool calls and results remain. Attachments and thread storage files are not exported.

### Test fallout from the strip (decided)

A full `turbo run test` after the strip failed 13 tests in `@bb/server`, `@bb/web`, `@bb/plugin-build` and `@bb/scripts` that use Docs, GitHub, Memory, Tasks or the Modal sandbox as live fixtures. Typecheck and build do not see this.

Decision (10 Nov): all 15 plugins stay removed. The strip script skips those tests from `scripts/fork/skipped-tests.json` (`b0385ceba3`, generated result `2296369e64`), so there are no hand edits to conflict. After it, the server, web and plugin-build suites pass.

## Version line, updates and releases (12 Nov)

**Version line.** BB Studio has its own semver, independent of bb's, in `apps/desktop/studio-release.fork.json`. It started at 1.0.0: copies installed before it report bb's 0.49.x, and electron-updater only offers a higher version, so anything below 1.0.0 would never reach them. `apps/desktop/package.json` keeps bb's version; the build replaces it. The "based on bb" label (Settings, the macOS About panel, release notes) names the nearest upstream `desktop-v*` tag at or before the fork base and the commits past it: "based on bb 0.50.1 @ a08e116" on the tag, "based on bb 0.49.0 + 168 commits @ d2fd338" past it. `identity.mjs` writes it to `apps/desktop/studio-upstream.json` (`version`, `commit`, `ahead`) with `git describe`; `sync.mjs --fetch` fetches upstream's `desktop-v*` tags. Without a tag it falls back to `apps/desktop/package.json`'s version and no count. Upstream bumps that version only when it prepares a release, so it is not a good label on its own. `scripts/build.mjs` ends its esbuild defines with `studioBuildDefines(readStudioBuild(process.env))` (`scripts/studio-release.fork.mjs`), so `BB_DESKTOP_VERSION` is the Studio version and `BB_STUDIO_BUILD` carries the version, the bb base from `studio-upstream.json` and the feed. `scripts/run-electron-builder.mjs` calls `applyStudioBuilderConfig`, which sets `extraMetadata.version` (the packaged `package.json`, `CFBundleShortVersionString` and `app.getVersion()`, the version electron-updater compares) and `publish`. About shows `Version: 1.0.0 (based on bb 0.49.0 @ 030b1b7)` (`studioAboutVersion` in `main.ts`); Settings, Updates shows the Studio version with "based on bb 0.49.0 @ 030b1b7" beside it: `ForkStudioBase.tsx` in `RowName` draws it next to any row whose version is the build's (`window.bbDesktop.experimental_studioBuild`). With the server run by the desktop, that row is "Server" and comes from the server's view of the desktop updater; `desktop-app-update.ts` reports the desktop's version there, since the bundled server's own version is bb's. It also records the desktop's version as the version an update starts from, and after the restart it counts a pending update as done when the desktop or the server runs the target version (`desktopVersionIfPending` in `desktop-app-update.fork.ts`), and leaves it pending when the desktop does not answer; 1.0.0 → 1.0.1 compared the Studio target with bb's version and showed "Update to 1.0.1 failed" after a good update.

**Updates.** The feed is the GitHub releases of `patleeman/bb-studio` (`provider: github`, no token), the public repository that is to hold the clean monorepo; it is `updates` in `studio-release.fork.json`. The app-update.yml in the bundle and the runtime `setFeedURL` both use it; upstream's version check reads `desktop-version.json` from `https://github.com/patleeman/bb-studio/releases/latest/download/`. `DESKTOP_UPDATES_ENABLED` is `STUDIO_UPDATES_ENABLED`: on in every build made by `scripts/build.mjs`. electron-updater offers only the latest published, non-draft, non-prerelease release, so drafts are never offered, and every published release must carry `latest-mac.yml`. While the repository has no published release with `latest-mac.yml` (on 12 Nov it is public with no releases; a private repository answers 404), every check fails: upstream's services log it to `desktop.log` and keep the state as it was, with no dialog and no toast. Settings, Updates shows "No BB Studio release found." with Check on the Server row (the message is `STUDIO_NO_RELEASE_MESSAGE` in `desktop-app-update.fork.ts`; the button's labels come from `forkStudioCheckLabel` in `ForkStudioBase.tsx`); nothing else (no sidebar badge). In a Studio build the row's Changelog is a link to `https://github.com/patleeman/bb-studio/releases` once the check found a release, and is hidden while it found none (`forkStudioReleaseLink`); bb's own changelog panel is never offered. The feed starts working, with no change to the app, when a release with the update files is published there. electron-builder writes `app-update.yml` only for a zip or DMG target: an install from `pnpm run package` (`--dir`) can see an update but not download it (logged, no dialog), so update-capable installs come from the release script's DMG.

**Release.** In the desktop worktree, with `CSC_NAME` set to the Developer ID identity and an App Store Connect API key for notarization (`BB_STUDIO_NOTARY_KEY_PATH`, `BB_STUDIO_NOTARY_KEY_ID` and `BB_STUDIO_NOTARY_ISSUER`, else `ASC_KEY_PATH`, `ASC_KEY_ID` and `ASC_ISSUER_ID` in `~/.config/bbgo/testflight.env`; with neither, the `bbstudio-notary` notarytool keychain profile). The script runs unattended on a locked Mac: it holds `caffeinate -i -w <pid>` for the whole run, never prints the key values, and before the build fails if the login keychain is locked (`security show-keychain-info`), `CSC_NAME` is not listed by `security find-identity -v -p codesigning`, or the key file is missing (`scripts/fork/release-unattended.mjs`, tests in `release-unattended.test.mjs`):

It folds the new version into the commit that owns `studio-release.fork.json` by rebasing the whole `desktop` stack, generated commits included, onto its base (`scripts/fork/release-bump.mjs`, tests in `release-bump.test.mjs`), so the source `desktop-release-work` is `desktop` plus the version and `sync.mjs`'s "tree is identical" check can pass (1.0.1's run handed it the hand commits only, and it could not). The 1.0.0 draft was made on the private `patleeman/bb-studio-app` with `--repo patleeman/bb-studio-app`; it is made again on `patleeman/bb-studio` when that repository takes the monorepo. `--from sign` or `--from publish` resumes; `--dry-run` checks and prints the plan. ## macOS privacy: Reminders and Calendars (15 Nov)

Agents run as child processes of BB Studio: the server and the host daemon are `BB Studio` itself with `ELECTRON_RUN_AS_NODE=1` (`bb-process.ts`), and agent shells and the CLIs they start (such as `reminders`) descend from them. macOS counts BB Studio.app as the responsible app for all of them, so a Reminders or Calendars request from a shell is asked against BB Studio's Info.plist and the hardened-runtime entitlements of its main executable. Without a usage text macOS denies the request with no prompt and never lists the app under Privacy & Security; bb had none either.

`applyStudioBuilderConfig` ends with `applyStudioMacPrivacy` (`apps/desktop/scripts/studio-mac-privacy.fork.mjs`), so there is no core edit:

- `mac.extendInfo` gains `NSRemindersFullAccessUsageDescription` and `NSCalendarsFullAccessUsageDescription` (macOS 14 and later) and `NSRemindersUsageDescription` and `NSCalendarsUsageDescription` (macOS 13).
- `mac.entitlements` is `build/entitlements.mac.fork.plist`: upstream's `build/entitlements.mac.plist` plus `com.apple.security.personal-information.calendars`, which covers Calendars and Reminders. The build fails when the two files differ by anything else, so an entitlement upstream adds must be copied in. `entitlementsInherit` stays upstream's: the Electron helpers (renderer, GPU, utility) never ask for Reminders or Calendars, and the processes that run agents are the main executable.
- The release (`verifyApp`) and `--build-only` check the built app's Info.plist and its signed entitlements (`studioMacAppProblems`). Test: `apps/desktop/test/studio-mac-privacy.fork.test.ts`.

A server moved to a launchd service (`apps/host-daemon/src/server-move`) is not a child of the app, so agents it runs are not covered by this.

## Bringing things over from bb, and the one-way mirror (10 Nov, reworked 19 Nov)

All of it is in `apps/server/src/services/fork-import/` (seam `import-sync`). Core has small hooks in seven files: `server.ts` registers the routes (which also start the jobs) and passes the plugin service, `start-server.ts` calls `forkBeforeDatabase`, `thread-send.ts` calls the fork's write guards, `thread-create.ts` asks the fork's host stand-ins before refusing a fork onto another machine, `dispatch-attempt.ts` lets an empty-input fork start without a turn while a limit is full, `apps/cli/src/commands/server.ts` registers the `bb server mirror` commands, and the CLI command index lists them.

**First start** (`first-run.ts`). BB Studio never reads `~/.bb` while it starts. `forkBeforeDatabase` only names the data dir and resets the rail preferences. Until 19 Nov it copied the whole bb install before the server listened; on a large install the launcher's 60 s health check (`packages/bb-app/src/launcher.ts`) killed it partway, and the copy brought bb's plugins along, which broke Studio.

**Bring things over** (`bring-over/`, routes under `/api/v1/fork/bring-over`). The user picks what comes over, while the server runs.
- **Source.** `~/.bb` for the packaged app (data dir `~/.bb-studio`), or the folder in `BB_STUDIO_IMPORT_FROM`; `off` turns it off (`import-source.ts`). Nothing in it is ever written.
- **Reading bb** (`source.ts`, `snapshot.ts`). `POST /fork/bring-over/snapshot` copies bb's database into `fork-bring-over/bb.db` in the data dir with SQLite's backup API in one step (one read transaction for all pages), in a child process: a bb that keeps writing can't reset it (a step-by-step backup restarts on every write and may never finish), and the child exits when its stdin pipe closes, so it never outlives the server. Listing and the job read that copy. The copy is 0600 in a 0700 folder, is deleted when a job finishes and is forgotten after an hour; it is not a server-owned path, so archives and server moves leave it out. `GET /fork/bring-over?summary=1` answers only whether bb is there and the last job (the first chat's link uses it).
- **Listing** (`listing.ts`, `settings.ts`, `plugins.ts`). Projects with thread counts, last activity, how many threads are already here and which BB Studio project they join; a project's threads; settings items, each saying what it is (`env` is marked secret); and bb's plugins without the built-in ones, the ones BB Studio bundles and the ones the fork removed (`HIDDEN_PLUGIN_IDS`, checked against `scripts/fork/removed-plugins.json` by a test).
- **Threads** (`threads.ts`). Rows keep bb's ids. Threads come over parents first; a link (parent, forked-from, lifecycle owner) is kept only when the other thread is here, otherwise cleared. A project comes along, unless BB Studio already has a project for the same folder on this Mac, which the threads then join. A folder on bb's machine moves to this machine at the same path (or to the environment BB Studio already has for it); folders on other machines keep their host. Running threads arrive idle. After the copied events, each thread gets a background-task `completed` event (task stopped, without `ownerStopped`) for every background task bb left open, and then one `system/operation` event, `brought_over_from_bb` (`settle.ts`). A restart interruption bb left as the newest event (`host-daemon-restarted`) is then no longer the newest, so neither core's restart resume nor Studio's "Resume after a restart" picks the thread up and starts an agent on its own. A mirrored thread gets the same step when it is taken over (`takeover.ts`); before that it can't be resumed, because every send and dispatch refuses a mirrored thread as read-only. Events, outlines, tabs, prompt history, search segments, context-file states and retained outputs come with the thread; plugin metadata does not. Each thread is one transaction (foreign keys deferred to the commit); its thread-storage files and, if picked, attachments are cloned under a temporary name and hard-linked into place first, and removed if the transaction fails or the job is cancelled. A thread already here is skipped, never updated. An environment bb manages (a provider's, one that owns its path, a worktree, or anything under bb's folder) never comes over: the thread arrives without it, so BB Studio's environment cleanup can never remove or reset bb's worktrees or stop bb's agents in them. A plain project folder comes over unmanaged (no provider, owner, retire or teardown). A thread with more than 5,000 events first stages its events in a temporary table on the server's connection, 2,000 at a time with the server yielding between them; then one last transaction writes the project, environments, thread and all its events from the staging table. Until then nothing of the thread is in `threads` (the deleted-thread sweep never sees a half thread); a failure or cancel drops the staging table.
- **Settings** (`settings.ts`): display preferences (without bb's rail and footer keys), app settings, theme, `AGENTS.md`, skills, custom models and environment variables. Each fills what BB Studio lacks unless the user asks to replace; the last two go into `config.json` and `env.json` and take effect after a restart.
- **Job** (`job.ts`). One at a time per data dir, in the server process, yielding between threads; progress counts, Cancel (`POST /fork/bring-over/jobs/current/cancel`), and the last result for `bb server mirror status`. Failure details are fixed texts or error codes, never raw error text.
- **Plugins** (`plugins.ts`). `POST /fork/bring-over/plugins/:id/add` copies the plugin's database (one-step backup), its `plugin_kv` and `plugin_settings` rows, then installs it from its recorded source (`installPath` for a folder, `install` for git or npm) and reloads it. Code is never copied: a git or npm plugin is fetched again from its source, and a folder plugin is installed from its folder only if that folder is on this Mac (otherwise it is listed as not found here and no row is written). A plugin whose `engines.bb` does not fit the running app is listed as needing a newer BB Studio and can't be added. An install that fails is reported and undoes the copied data; the undo removes only a plugin id this Add installed, never one BB Studio already had. Secrets folders never come over. No plugin row is ever brought for an id BB Studio bundles or the fork removed (a dead path install of `studio` from bb hid the bundled Studio on 1.0.7). A git or npm plugin installs bb's exact commit or version (`git:<url>@<commit>`, `npm:<name>@<version>`); if bb did not record it, or it can't be fetched, nothing is installed. The installed manifest is checked: a plugin that installs under another id, or one BB Studio bundles or removed, or whose `engines.bb` doesn't fit, is removed again. Its values go in with INSERT OR IGNORE and only the keys written are taken back out; one Add per plugin at a time.
- **Agent Plugins → Tool Gateway** (`tool-gateway.ts`, 20 Nov). Agent Plugins is never added to BB Studio (`addPlugin` refuses `agent-plugins`); Studio's Tool Gateway imports its servers instead. `POST /fork/bring-over/tool-gateway/stage` (gated like the other bring-over routes) copies bb's `plugins/agent-plugins/data.db` with the same one-step backup to `plugins/studio/secrets/tool-gateway/agent-plugins-import.db` (folders 0700, file 0600). It holds plain-text env and header values, so it sits in Studio's secrets folder: never copied by a bring-over, kept in place by the Studio-data swap, and outside `import-staged`, so staging Studio data neither replaces nor deletes it. bb's secrets folder is not copied. Studio reads the staged file, the user's tick in the app window approves each server, and Studio deletes the copy once the import has run (or failed), or when the user discards it.
- **BB Studio data** (`studio-data.ts`). `POST /fork/bring-over/studio-data` only stages: one snapshot child run copies bb's database and bb's `plugins/studio/data.db` together, Studio's other files come along except secrets, logs, host data, bridge data, backup sessions and database sidecars, and bb's `studio` plugin_kv and plugin_settings rows go to `bb-kv.json` (0600). All of it lands in `plugins/studio/import-staged/` (0700) with a `journal.json`. The threads Studio's data names come over as an ordinary bring-over job whose request carries `studioData.required`; the job is refused when one of them is not in bb or bb was read again after the copy, and when it ends with them all here the journal turns `ready`. The server applies nothing: the Studio plugin swaps the staged data in at its next start (first load in the server process only) and writes `applying`, `applied`, `rolling-back` and the rest itself. Discard, put-back (a request the plugin carries out at its next start) and forget follow the journal's state. A journal that can't be read or has an unknown state refuses every action and shows as `unreadable`; copy and discard also refuse while `before/` or `replaced/` exists. Every POST needs the UI token; staging is refused while another bring-over runs. `GET /fork/bring-over/studio-data` answers the state the plugin's row reads; a server without this group answers 404 there.
- **bb's environments already here** (`bb-environments.ts`). At server start and at the end of every mirror tick, an environment row whose path (or claimed path) is under bb's data folder and that a provider manages, owns its path, or is set to retire or tear down is made plain (no provider, owner, retire or teardown), so BB Studio's environment cleanup never removes or resets bb's worktrees that came over in an earlier, automatic import. Destroyed rows count too unless their teardown finished (`removed`). The mirror tick is synchronous, so no sweep runs between the copy and the release.
- **Never copied:** host identity (`host-id`, `auth.json`), bb's `auth-secret` and the machine keys it issued, `telemetry-id`, plugin folders other than through Add, worktrees, logs, and anything in flight (queued messages, approvals, terminals, daemon sessions).

**Installs imported before 19 Nov** keep their mirror: their threads stay read-only until taken over and the jobs below keep running; if bb's folder is gone or renamed, they skip quietly. The jobs' timer starts only on an install that has a mirror (`fork-import.db`); nothing on a new install starts it. `~/.bb/pi-bridge-sessions` is never moved or deleted (nothing writes to `~/.bb`).

**Sync** (`sync.ts`, every minute as the job `fork-import-sync`). The fork's two jobs (`fork-import-sync`, `fork-import-thread-storage`) run on their own 10-second timer (`sweeps.ts`), started by `registerForkImportRoutes` only after `forkBeforeDatabase` named the data dir. They keep bb's sweep rules: per-job cadence, background jobs not awaited, no overlap, nothing while a server move has frozen the database, not started on a pending move target, and stopped on SIGINT/SIGTERM. Upstream's `periodic-sweeps.ts` is not edited. Projects, thread sections and environments are upserted by `updated_at`. A thread is copied again when its row changed or it has new events (found by event rowid above the last one seen). New events are appended; when the count of earlier events differs (bb prunes and deletes events), that thread's events are reloaded. The thread's per-thread tables are reloaded with it. Threads deleted at the source are removed here (checked every 10 minutes). Environments keep the source machine as their host, so BB Studio never runs cleanup on a folder bb still uses. `fork-import.db` in the data dir holds the cursors and the list of mirrored threads.

**Mirrored threads are read-only** until taken over: `ensureThreadIsWritable` calls the fork's write guards (`services/threads/thread-write-guards.fork.ts`, one line in `thread-send.ts`), and the import registers one that refuses a mirrored thread with a 409 `thread_read_only`, details `{ reason: "mirrored" }` and the mirror message. It is not a `thread_not_writable` reason: the app draws those with fixed copy per reason, and none fits; for any other error code the app shows the server's message, so the contract enum and `lifecycle-errors.ts` stay upstream's. **Take over** (`takeover.ts`) is refused while the thread is running or has queued messages at the source. It runs one last sync, moves the thread's environment to this machine, and stops syncing that thread and that environment. From then on the two copies are separate.

**A thread from a mirrored message.** A fork must run on its source thread's machine, and a mirrored thread's environment stays on bb's machine, which never connects to BB Studio. `assertForkSourceHost` (`thread-create.ts`) asks the fork's host stand-ins first (`services/threads/thread-fork-hosts.fork.ts`); the import registers one that lets a mirrored, not taken over thread whose environment is on the imported bb machine fork onto this machine. The new thread is BB Studio's own: it copies the history up to the message, starts no turn and writes nothing to bb. The mirrored thread stays read-only and its environment stays on bb's machine. Reply in thread forks with an empty input, which upstream starts as an idle fork with no turn. Upstream still sent that first dispatch through the plugin hooks and core waits, so a full concurrency limit queued an empty message that every later read rejected with "Stored queued message … is malformed". `startsNoTurn` (`services/threads/turnless-dispatch.fork.ts`) marks the first dispatch of a pending fork with no input: `dispatch-attempt.ts` skips the plugin hook pass for it, so the limit does not hold it, and a core wait (an update hold, an offline host) leaves the fork pending instead of queueing an empty message. A fork with input is held and queued as before. Studio's Reply in thread and Fork conversation from here pick the environment here (a ready environment for the same folder, else a personal workspace in the personal project, else the folder, else the project default).

**Commands.** `bb server mirror status | sync | pause | resume | thread <id> | take-over <id>`; the routes are under `/api/v1/fork/import`.

**Not covered.** An event edited in place at the source without a new event is not noticed until that thread's event count changes. Projects, thread sections and environments deleted at the source stay here.

## Drag and drop audit

One payload for "an item" (thread, doc, tab, file): MIME `application/x-bb-item`, written with `experimental_writeDragItem`. Studio owns its sources and targets; bb's composer, workbench and main view take the payload through `slots.experimental_itemDrop` (`ForkItemDropHost.tsx`). The Studio copy with footnotes is `packages/bb-studio/docs/dnd-audit.md` in the Studio repository.

Workbench drops (11 Nov): over a pane's tab row the target is `{ zone: "workbench", threadId, pane: 1 | 2, index, open }` and bb draws an insertion bar between the tabs; over the right edge of a single pane it is `pane: "new"` and bb highlights the right half with "Split right", as for a tab dragged there; elsewhere in the panel it is `{ zone: "workbench", threadId, open }` with the outline, as before. The handler opens the item with `target.open(spec, { pane, index })`, the panel's own `experimental_workbench(threadId).open`. Core code only reports where; whether a drop elsewhere opens anything is the handler's `canDrop`.

Native tab drags and popped-out windows (11 Nov, evening): every side panel tab is a native drag source (`usePanelTabNativeDrag`), so a tab can leave the window with the browser's drag image. The mouse no longer runs dnd-kit's reorder or bb's pane pointer drag; a tab dropped on a tab row is bb's own move (`fork-tab-move.ts`): reorder or pane change in its own window, open-from-`open` in another panel or window with the source closing on `dragend` `dropEffect` `"move"`. A popped-out window is a workbench panel of the thread with its own tab state (`ForkTabWindowPanel.tsx`), taking the same drops as the main panel through the same host and handler.

Cells: **works** = code and tests; **moves** = bb's own move, no handler; **not** = gap; n/a = not meaningful. Nothing here was dragged by hand in the desktop app; a drag between two windows cannot be run headless.

| Source ↓ / Target → | Main panes (tab row, body, right edge) | Popped-out window tab row | Sidebar rows | Composer | Main view |
| --- | --- | --- | --- | --- | --- |
| Sidebar row (conversation, worker, Bot page, Library) | works | works (through `target.open`) | Studio's own | works | works |
| New Tab or Recent row | works | works | n/a | works | works |
| Main window tab (plugin action, workspace, host, thread storage file) | moves (reorder, other pane, new pane) | moves (opens there, source closes) | not [1] | works (Studio tabs: a pill; bb files: refused) | works (Studio tabs move there; bb files: refused) |
| Main window tab (terminal, browser, Info, Diff, New Tab, fixed) | moves within its panel | refused, no-drop cursor | not [1] | refused | refused |
| Popped-out window tab | moves (opens there, source closes) | moves (reorder, other pane, new pane) | not [1] | works (Studio tabs) | works (Studio tabs) |
| Finder file | not | not | not | n/a (bb attaches) | not |

Gaps: [1] Studio's sidebar rows take no drops from bb (filing is Studio's own); a drop that nothing takes in another window leaves the source as it was, since the source learns of the drop only from `dropEffect`; a tab window closed with its close button drops its tabs; touch still reorders through dnd-kit and cannot leave the window.

## Syncing with upstream (10 Nov)

**Stack order.** The branch is four layers on top of the upstream base:

1. `fork: rules, tooling and notes`: the scripts in `scripts/fork/`, this file, `docs/api_to_audit.fork.md`, and one line each in `AGENTS.md`, `CLAUDE.md` and `vitest.shared.ts`.
2. Seams. `seam: SDK tables` holds every fork edit to the SDK's shared files, the backend contract and the Plugin Guide. `seam: core hooks` holds every upstream app, server and desktop file that more than one seam edits (`AppLayout.tsx`, `plugin-api.ts`, `plugin-service.ts`, `lifecycle/run.ts`, `apps/server/src/server.ts`, the desktop `main.ts` and `preload.ts`, `desktop-contract/src/info.ts`, `plugin-navigation-hooks.ts`, `ThreadScreen.tsx`, `SecondaryPanelTabStrip.tsx`, `ThreadTimelineRows.tsx`). The other `seam:` commits hold the implementations and the core files only they edit.
3. Features: one commit per area (search, workbench, sidebar, quiet turns, layout and composer, import, diff, polish).
4. Generated commits at the tip, each with a `Fork-Generated:` trailer: strip, identity, rebrand. Never rebase these. Drop them and run the scripts again.

Each upstream file the fork edits is in exactly one hand commit, so a conflict in it stops one pick. Add new work as a new commit in layer 2 or 3 (below the generated commits), or fold it into the commit for its area; an edit to a file that `seam: SDK tables` or `seam: core hooks` already holds goes into that commit.

**Rules that keep conflicts small.**

- Run `oxfmt` only on fork-owned files, never on an upstream file the fork touches.
- A new slot goes in `packages/plugin-sdk/src/internal/fork-slots.ts` and `apps/app/src/lib/fork-slots.ts`, not in the upstream tables.
- A test the fork breaks on purpose goes in `scripts/fork/skipped-tests.json`. `scripts/fork/vitest-skips.ts` skips it at run time; test sources stay as upstream wrote them.
- Edits that only exist because plugins were removed (registry, marketplace list, stories, Plugin Guide examples) live in `scripts/fork/patches/unregister.patch`. To change it: reverse it (`git apply -R`), edit the files, and write the diff of those files back to the patch.
- API audit entries go in `docs/api_to_audit.fork.md`.

**Regenerating by hand.** Order matters: `node scripts/fork/strip-plugins.mjs` (it runs `pnpm install`), then `node scripts/fork/identity.mjs`, then `node scripts/fork/rebrand.mjs`. The rebrand needs the install first because the app's icon generator imports `sharp`.

**Who syncs.** An agent does, daily, from a bb automation; `scripts/fork/sync-agent.md` is its brief. It resolves conflicts itself and reports only when it could not, or when checks fail. Sync cost is measured in conflicts and how hard each one is. The rules that keep them easy are in `AGENTS.fork.md`; `scripts/fork/core-edits.json` records the intent of every core edit, and `scripts/fork/check-core-diff.mjs` enforces the list and the line budgets.

**`scripts/fork/sync.mjs`.** `node scripts/fork/sync.mjs --fetch` replays the fork onto `upstream/main` in a throwaway worktree under `../.bb-studio-fork-sync/`: it cherry-picks the hand commits (git rerere replays recorded conflict resolutions), checks the core diff against the ledger, runs the three scripts, commits their output with the trailer, and runs typecheck, build and the server, web, plugin-build and SDK tests (`--checks none|quick|full`). It writes a report beside the worktree. On success it moves the local branch `exp/studio-native-candidate` and nothing else; it never checks out or moves `exp/studio-native`, and it pushes nothing. On a conflict it stops, leaves the worktree, and prints the commands to continue. With `--onto` set to the current base it is a reproduction check: the result must have the same tree as the source branch.

## Monorepo (12 Nov)

The fork lives in the BB Studio monorepo, on its `desktop` branch. It replaces the local-only branch `exp/studio-native` of the old `bb` clone; where older sections of this file say `exp/studio-native`, `exp/studio-native-candidate` or `bb-studio-native`, read `desktop`, `desktop-candidate` and `bb-studio-public-desktop`.

- **`desktop` branch** (worktree `~/workingdir/bb-studio-public-desktop`): this stack, unchanged in shape. Paths are bb-root-relative, it descends from `upstream/main`, and each sync rewrites it. The ledger, `check-core-diff.mjs` and the reproduction check run here.
- **`main` branch** (worktree `~/workingdir/bb-studio-public`): the monorepo. `desktop/` there is a tree snapshot of this branch, written by `scripts/import-desktop.mjs` as a merge commit whose second parent is the stack tip. Nobody edits `desktop/` on `main`. `plugins/` there is the Studio plugins with their history, in their own pnpm workspace.
- **Invariant:** `git rev-parse main:desktop` equals `git rev-parse 'desktop^{tree}'` (`node scripts/import-desktop.mjs --check` on `main`).
- **Scripts.** `sync.mjs` defaults to `--source desktop --candidate desktop-candidate`, refuses to run inside `main`'s `desktop/`, and takes its work folder from `BB_STUDIO_SYNC_DIR` (default `../.bb-studio-fork-sync`, as before). `check-core-diff.mjs` has the same refusal. `build-plugins.mjs`, with no arguments and no `~/.bb-studio-import.json`, builds every package in `../bb-studio-app/plugins/packages`.
- **Remotes.** `origin` is the BB Studio repository (the `pre-push` hook on `main` names it). `upstream` is `get-bb/bb` with the push URL set to `DISABLED`, only `main` fetched and no tags. A `pre-push` hook on `main` (`scripts/git-hooks/pre-push`) refuses every other remote and every ref but `main`, `desktop` and `v*` tags. GitHub Actions is off for the repository, so upstream's workflows at this branch's root do not run.

Daily flow:

1. `node scripts/fork/sync.mjs --fetch` here. It moves only `desktop-candidate`.
2. Promote: `git reset --hard desktop-candidate` on `desktop`, with a clean tree.
3. `node scripts/import-desktop.mjs` on `main`.
4. `git push origin main && git push --force-with-lease origin desktop`.

A core change outside a sync: commit it below the generated commits, run `check-core-diff.mjs`, regenerate with `node scripts/fork/sync.mjs --source <work branch> --onto <current base> --candidate desktop-candidate`, promote, import. `docs/REIMPORT.md` on `main` has the commands.

### Methods

- Event Horizon traces light through a Schwarzschild black hole. Each ray from the camera is stepped with the photon orbit equation in Cartesian form, `a = -3/2 · h² · x / r⁵` (Schwarzschild radius 1, `h = |x × v|`), which gives the same path as the Binet equation `u'' + u = 3Mu²`. The step is 0.12·r, so a pixel takes more steps near the hole and none when its ray misses the 18 r_s sphere; outside that sphere the weak-field angle `2 r_s / b` bends the ray. The disk runs from the innermost stable orbit (3 r_s) to 16 r_s with the Novikov–Thorne flux profile `F ∝ r⁻³(1 − √(r_in/r))`, temperature `T ∝ F^¼`, Keplerian speed `β = √(M/(r − 2M))`, and the shift `g = √(1 − r_s/r) / (γ(1 − β·n))`. Observed temperature is `g·T` and brightness `g⁴·F`, so the approaching side is brighter and bluer.
- Forest's sun is placed with the low-precision solar coordinates of the Astronomical Almanac (accurate to about 0.01° between 1950 and 2050): day above 6°, night below −6°, dawn or dusk in between. With no place, the clock stands in: sunrise at 6:30, sunset at 18:30.
