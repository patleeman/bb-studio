# Duo v6: quick replies and system insets

The Bot quick-reply horizontal scroll view disabled clipping. Its viewport
already matched the composer, but the extra chips could draw past that viewport
into the system's trailing safe area. It now uses normal scroll clipping;
horizontal scrolling reveals the remaining replies inside the composer edges.
No root layout, system safe area, keyboard or transcript scrolling behavior changed.

The UI regression test records native UIKit scroll-view geometry and checks the
laid-out content edge against the window safe area. It also checks the quick-reply
viewport against the composer and requires clipping. The baseline scroll view
reported `clips=false`; this is the specific overflow regression assertion.

- [Dark Bot render, iPhone idiom at 951×669](v6-bot-duo.png)
- [Window and native scroll-view measurements](v6-capture-geometry.json)

At 951×669 pt, the window reports an 84-point trailing safe area and a
34-point bottom safe area. The native transcript scroll frame extends to x=951,
while SwiftUI lays out its content to x=867 (375.33-point content width starting
at x=491.67). That reserves the window's 84 points once. The quick-reply viewport
and composer both span x=503.67…855, retaining the existing 12-point inner margin.
The composer ends at y=627: 669 − 34 system inset − 8 existing padding.
The rail and system insets were left unchanged; the spaces protect the status
column and home indicator rather than coming from a second app inset.

Validation: all 341 iOS unit tests completed with one skip and no failures;
Studio typecheck and 1,982 Vitest tests passed. The clipping regression UI test
checks the layout above. No TestFlight build or upload ran.
